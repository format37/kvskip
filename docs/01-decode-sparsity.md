# Attention Sparsity Study — kickoff

Цель первого этапа: получить честную картину того, как распределяется внимание
в открытой LLM на реальном длинном контексте — по слоям, головам и KV-блокам —
и оценить, сколько блоков можно пропускать динамически без потери качества.
CUDA-ядро пишем *после* того, как цифры скажут, что оно оправдано.

Железо: RTX 4090 (Ada, sm_89, 24 GB). Нет wgmma/TMA — сравнивать потом с FA2, не FA3.

---

## 0. Веса: почему не ollama

Ollama хранит GGUF, обычно Q4_K_M. Для исследования нужны оригинальные bf16
safetensors: мы будем подменять attention внутри HF-модели и сравнивать с fp32/fp64
референсом, квантованные веса всё это исказят. Берём raw с Hugging Face.

Модели:
- `meta-llama/Llama-3.2-1B-Instruct` — рабочая лошадка для итераций (forward за секунды)
- `meta-llama/Llama-3.1-8B-Instruct` — основной объект
- `Qwen/Qwen3-8B` — позже, для проверки, что паттерны не артефакт одной тренировки

Llama — gated: принять лицензию на HF, `hf auth login` с токеном.

```bash
hf download meta-llama/Llama-3.2-1B-Instruct --local-dir models/llama-3.2-1b
hf download meta-llama/Llama-3.1-8B-Instruct --local-dir models/llama-3.1-8b
```

## 2. Точка врезки

В `transformers>=4.48` attention — подменяемая функция через
`ALL_ATTENTION_FUNCTIONS`. Регистрируем свою `"probe"`-реализацию:

1. Сначала **чистый PyTorch eager** с материализованной матрицей весов —
   это ground truth и источник статистики. Медленно и прожорливо, но на 1B
   при 8k контексте влезает; для 8B на 32k считать статистику по чанкам Q.
2. Потом CUDA-ядро, которое считает ту же статистику онлайн, не материализуя
   softmax (flash-style, m/l в регистрах + счётчики на блок).
3. Проверка: статистика из (2) == статистика из (1) с точностью до bf16.

Важно разделять **prefill** и **decode**: интересует именно decode —
один query против всего KV. На prefill картина другая и менее важна для инференса.

## 3. Что считаем (per layer × per head, блок KV = 64 токена)

- энтропия весов softmax (в битах, нормированная на log2(T))
- sink mass: доля веса на первых 4 токенах
- доля блоков, чей суммарный вес < 1e-3, < 1e-2
- сколько блоков нужно, чтобы набрать 0.9 / 0.99 массы
- **GQA-union**: для каждой KV-головы — объединение «нужных» блоков по её
  4 query-головам. Это реальный предел выигрыша от пропуска блоков.
- pre-exp критерий: max(QK^T) по блоку vs глобальный max m — можно ли решать
  «пропустить» ДО exp. Коррелирует ли с фактическим вкладом блока.

Агрегировать по токенам decode: средние, медианы, хвосты (95-й перцентиль).

## 4. Данные

Нужны тексты длиннее контекста, на котором что-то можно выкидывать:
- 1B: 4k–8k (проза, код, длинный multi-turn диалог — три разных жанра)
- 8B: 16k и 32k

Сценарий: prefill на документе, затем 64–128 шагов decode (например, запрос
«summarize» или вопрос по тексту, ответ на который лежит далеко от конца).
Фиксировать seed, greedy decoding, чтобы прогоны были воспроизводимы.

## 5. Первая абляция (ещё без своего ядра)

Маскируем блоки, чей вес ниже порога, прямо в eager-реализации, и меряем:
- KL(logits_ref || logits_masked) на каждом шаге decode
- расхождение greedy-текста: на каком шаге впервые разошлось
- то же при пропуске по pre-exp критерию (QK-max), а не по фактическому весу

Сетка порогов: 1e-4, 1e-3, 1e-2. Отдельно: пропуск по GQA-union vs по голове.
