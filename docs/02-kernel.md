# kvskip — kickoff этапа 2: решить, какое ядро, и построить пол под него

Итог этапа 1 (`docs/01-...`): бесплатно выбрасывается ~половина V-блоков по GQA-union,
хвост внимания функционален (top-p 0.9 → KL ×10), pre-exp ранжирует почти как оракул,
а набор блоков почти не меняется между шагами (97% массы от набора 16-шаговой давности).

Последний факт — развилка. Если переиспользование выбора проходит абляцию, ядро пропускает
и K, и V с периодическим refresh. Если нет — двухпроходный V-skip. Эти два ядра делят
80% кода, поэтому этап 2 идёт двумя дорожками параллельно: A решает, B строит общее.

---

## Дорожка A — абляции, которые решают архитектуру (1–2 дня)

**A1. Переиспользование выбора (главный эксперимент).**
Refresh раз в N ∈ {1, 4, 8, 16, 32} шагов: на refresh-шаге полный проход и запись набора
(top-p 0.99, union по GQA); между ними грузятся только сохранённый набор + блок с sink +
2 последних блока. 8B, 16k и 32k, три жанра. Метрика как в этапе 1: KL vs fp32-эталон
относительно bf16-шума, top-1, потеря массы. Отдельно посмотреть p95 KL по шагам —
refresh-режим будет ломаться не в среднем, а в момент, когда модель «перепрыгивает»
на другой участок контекста. Если такие прыжки есть — где они (слои 8–11?) и предсказуемы ли
по падению покрытой массы (можно ли триггерить refresh по дешёвому сигналу, а не по таймеру).

**A2. Локальность масок.** Для union-масок top-p 0.99: распределение длин прогонов
оставленных/пропущенных блоков, доля блоков в прогонах ≥ 4. Это определяет, стоит ли
ядру работать с runs вместо битовой маски, и выгодно ли укрупнять блок до 128.
Если токенные веса сохранены — пересобрать статистику для блоков 32 и 128 без прогона.

**A3. Perplexity-проверка «бесплатности».** Held-out продолжение ~2k токенов, teacher
forcing, три условия: без маски / top-p 0.99 union / bf16 стоковое ядро. Одна таблица.
Закрывает возражение, что KL/шаг на 128 шагах не ловит накопление.

**A4 (если останется время).** Гипотеза про chat template как sink: тот же диалог без
template, та же проза с вставленными служебными токенами. Плюс по одному новому документу
на жанр, чтобы «диалог разреженнее» перестало быть n=1.

**Decision gate.** N ≥ 8 при KL на уровне шума → основной режим ядра: refresh.
Иначе → двухпроходный V-skip. В обоих случаях ядро из дорожки B пригодно, меняется только
планировщик.

## Дорожка B — ядро: бейзлайн и плотная версия

**B0. Дампы.** Из probe сохранить реальные q/k/v нескольких decode-шагов 8B
(несколько слоёв: 0, 9, 21, 31; 32k) → `data/kv_dumps/*.safetensors`. Тесты ядра гоняются
на реальных распределениях, а не на randn: gap'ы QK в 20–30 nats и bf16 — это там, где
онлайн-softmax ошибается.

**B1. Харнесс.** `kernels/` + `bench/`:
- сборка через `torch.utils.cpp_extension.load` (ninja уже есть), `-arch=sm_89`;
- корректность: против fp32-референса на дампах, порог — не хуже FA2 (отн. ошибка ~2e-3);
- тайминг CUDA events, warmup, медиана из 50; один слой, bs ∈ {1, 8, 32}, ctx ∈ {8k, 32k, 64k, 128k}
  (один слой в 128k — это 1 GB KV, влезает);
- метрика: мкс/шаг и достигнутая пропускная способность в % от ~1008 GB/s у 4090.

**B2. Бейзлайны.** SDPA и `flash_attn_with_kvcache` (FA2) в том же харнессе. Записать
числа до того, как написана первая строчка ядра — это планка.

**B3. Плотное split-K flash-decoding ядро, raw CUDA под Ada.**
- GQA-упаковка: одна KV-голова и её 4 query-головы в одном блоке потоков, K грузится один раз;
- KV режется на чанки по блокам потоков (split-K), каждый отдаёт частичные m, l, acc;
  второй маленький kernel делает редукцию;
- на Ada есть `mma.sync` (Ampere-style), нет wgmma/TMA; decode memory-bound, так что
  сначала простой путь: FMA + cp.async в shared, тензорные ядра — потом, если профиль покажет
  упор в compute;
- цель: ≥ 85% пропускной способности FA2 на 32k, bs=8. Без этого sparse-версию
  сравнивать не с чем.

**B4. Крючки под разреженность (в том же ядре, флаги).**
- вход: битовая маска блоков на (batch, kv_head); замаскированный блок не грузится ни K, ни V;
- режим `stats`: на выходе per-block max и sumexp — это refresh-проход для A1-режима и
  первый проход для V-skip;
- всегда плотно: слой 0 (решается на уровне Python, не ядра).

Планировщик на Python собирает из этого либо «stats → маска → masked», либо «masked N−1 раз,
stats раз в N». Оба режима — один kernel.

## Порядок

1. B0 и B2 — сразу, они быстрые и дают числа для отчёта.
2. A1 параллельно с B3 (абляция считается на GPU минутами, ядро пишется часами).
3. A2/A3 — пока ядро компилируется.
4. B4 — после decision gate.
