# kvskip — kickoff этапа 3: доказать выигрыш там, где он должен быть

Итог этапа 2 (`docs/02-kernel-digest.md`): плотное ядро на потолке полосы, K+V-skip с refresh
по триггеру держит качество при −39% байт, но единственный режим, который уже быстрее SDPA
end-to-end, — однопроходный V-skip на 1–6%. На bs=1/32k attention — 18% шага, потолок
выигрыша 7%. Вся ставка — на bs ≥ 8 и/или 64k+, и это не измерено.

Поэтому порядок этапа 3 — сначала проверка цели, потом оптимизация. Слияние планировщика
в ядра — большая работа, и её стоит делать только когда известно, что она окупится.

Первая задача, до всего остального: fast-forward `main` на stage-2, теги `stage-1` и `stage-2`.

---

## Фаза 1 — есть ли выигрыш вообще (полдня, с текущим Python-планировщиком)

**1.1. e2e на нагрузке, где KV доминирует.** 8B, режимы: SDPA, kvskip dense, V-skip-1,
refresh-по-оценке. Сетка: bs ∈ {8, 32} × ctx ∈ {32k, 64k}. На bs=32/64k KV слоя не влезет
вместе с весами — тогда 64k только на bs=8, и это надо зафиксировать, а не обойти молча.
Python-планировщик пока как есть: его накладные расходы амортизируются по батчу, и на bs=8
он уже близок к нулю (×1.25 в этапе 2 на одном слое). Метрика — мс на шаг для всего батча
и доля attention в шаге.

**1.2. Разложение шага.** Для каждой конфигурации: байты весов / байты KV / всё остальное,
и сколько из KV реально пропущено. Это даёт верхнюю границу выигрыша без всяких ядер
и показывает, насколько текущая реализация к ней близка.

**Gate.** Если на bs=8/64k refresh-режим даёт < 10% на шаг даже по верхней границе —
проект меняет цель (prefill, или KV-компрессия как соседняя тема), а не планировщик.
Если ≥ 20% по границе и ≥ 10% фактически — фаза 3 оправдана.

## Фаза 2 — две дешёвые идеи (параллельно с фазой 1)

**2.1. Индекс для induction-голов.** Гипотеза: 8 «всегда точных» голов — головы типа
«предыдущее вхождение текущего токена», и их цель вычислима без K.
- построить на prefill инвертированный индекс token_id → список блоков (можно bitset на токен,
  32k/64 = 512 бит; для словаря 128k это 8 МБ на последовательность — ок);
- на decode для каждой из 8 голов набор = блоки с текущим токеном (+ sink + 2 последних);
- проверить на probe: покрытие массы и KL для каждой головы отдельно. Сколько из 8 голов
  индекс закрывает полностью, какие нет — и что делают те, что нет (может, не induction,
  а «предыдущий токен», или copy по биграмме: тогда индекс по паре токенов).
- Если работает — это 3% байт обратно и, важнее, переносимый механизм вместо списка номеров.

**2.2. Триггер до прохода.** Оценка потерянной массы зависит от q, центроидов и статистики
refresh — всё есть до attention. Порядок шага: триггер → для сработавших голов плотный проход
со статистикой, для остальных masked. Никогда оба. Пересчитать «прочитано блоков»: ожидаю,
что 73/71/48% станут ~60/60/42%. Пока в Python, в ядро — в фазе 3.

## Фаза 3 — планировщик в ядра (только после gate фазы 1)

**3.1. Ядро выбора.** Один CTA на (batch, KV-голова): вход — per-block max и sumexp
со stats-прохода, выход — список блоков top-p 0.99 union по 4 головам. nb ≤ 2048,
сортировка в shared (bitonic или radix по экспоненте). Это убирает softmax+sort из Python.

**3.2. Триггер в masked-ядро.** Masked-проход и так читает q; центроиды блоков (1/64 K)
читаются в том же ядре, оценка потерянной массы пишется в маленький буфер. Второй мелкий
kernel принимает решение и формирует список голов на refresh.

**3.3. Один шаг без синхронизаций с хостом.** Всё решение — на девайсе: decision-буфер →
выбор ядра через indirect launch или через единое ядро с ветвлением по флагу головы
(dense vs masked). Второй вариант проще: одно ядро, флаг на голову, обе ветки внутри.

**3.4. CUDA graph на весь decode-шаг.** После 3.3 шаг статичен по структуре, и graph снимает
накладные расходы запуска: на bs=1 это как раз те 20%, что сейчас теряются на 8k.
`GrowingCache` уже есть; проверить, что буферы не переаллоцируются внутри графа.

**3.5. Повторить 1.1** с ядрами вместо Python. Это главная таблица этапа.

## Фаза 4 — переносимость (если останется время)

**4.1. Qwen3-8B.** Collect + A1-диагностика из этапов 1–2 без изменений. Вопросы:
слой 0 плотный? те же «контентные» слои? прыжки есть и такие же массовые? какие головы
«невидимы» для триггера — и закрывает ли их индекс из 2.1?

**4.2. Автокалибровка «точных» голов.** Один diag-прогон на новой модели → список голов
с «невидимыми» потерями → сначала попробовать индекс, потом «всегда плотно». Скрипт,
а не ручной отбор.

**4.3 (идея, не задача).** Шаблон как сегментация: вставить в прозу границы глав/разделов
в формате реплик и посмотреть, упадёт ли доля блоков с 57% к диалоговым 40%. Если да —
разреженность можно *наводить* форматом промпта, и это отдельный результат.

## Не делать на этом этапе

- Блок 32: только после 3.1–3.2, иначе удвоение метаданных ляжет на Python.
- Prefill: отдельный этап, другая экономика (compute, pre-exp-ранг).
- Тензорные ядра в плотном ядре: FMA на потолке полосы, незачем.
